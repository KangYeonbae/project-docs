## 어떤 프로젝트였나

공간 대여 플랫폼입니다. 사용자가 공간을 검색하고 예약합니다.

목표는 기능 구현 자체보다 **마이크로서비스로 나눠 팀이 독립적으로 개발·운영하는 경험**이었습니다. 교육 과정의 팀 프로젝트로, 분산 시스템의 실제 비용을 겪어보는 것이 목적이었습니다.

## 어떻게 나눴나

### 기능이 아니라 변경 이유로 분리

공간 정보와 예약 상태는 성격이 다릅니다.

| | 공간 정보 | 예약 상태 |
|---|---|---|
| 변경 주기 | 드물게 | 계속 |
| 변경 주체 | 공간 주인 | 이용자 |
| 정합성 요구 | 낮음 | 높음 (중복 예약 방지) |

**변경 주기와 책임이 다르면 별도 서비스 경계로 봤습니다.** 그리고 나누기로 정한 다음, 코드보다 **API 계약을 먼저 맞췄습니다.** 서비스 경계가 곧 팀 간 계약이기 때문입니다.

## 내가 한 일

**기여도 35%** — 팀 프로젝트입니다.

| 영역 | 담당 |
|---|---|
| Frontend | 사용자 화면 |
| API 연동 | 분산된 서비스 응답을 하나의 사용자 흐름으로 조정 |

백엔드 서비스 구현과 인프라는 팀원들이 담당했습니다. **제가 하지 않은 부분을 제 것으로 적지 않았습니다.**

## 이 역할에서 겪은 것 — 통합 비용

프론트엔드와 API 연동을 맡으면서 **MSA의 비용이 어디서 나오는지**를 직접 겪었습니다.

화면 하나를 그리는 데 여러 서비스의 응답이 필요합니다. 그러면 이런 것들이 따라옵니다.

- 한 서비스가 느리면 화면 전체가 느려집니다
- 한 서비스만 실패했을 때 화면을 어떻게 보여줄지 정해야 합니다
- 서비스마다 오류 형식이 다르면 사용자에게 보여줄 메시지를 통일하기 어렵습니다

**분산의 비용은 대개 통합하는 쪽에서 지불합니다.** 서비스를 나누는 결정은 백엔드에서 내리지만, 그 결과를 하나의 화면으로 다시 합치는 일이 프론트엔드에 남습니다.

이걸 겪고 나서 서비스 경계를 볼 때 "이렇게 나누면 화면에서 어떻게 합쳐지는가"를 함께 보게 됐습니다.

---

## 이 프로젝트에서 배운 것

**서비스 경계는 API 계약을 먼저 맞춰야 합니다.** 코드부터 짜면 나중에 인터페이스를 맞추느라 양쪽을 다 고치게 됩니다.

**나누는 이유가 명확해야 합니다.** "기능이 다르니까" 나누면 서비스가 계속 늘어나고 통합 비용만 커집니다. 변경 이유와 책임이 다른지를 기준으로 삼는 편이 나았습니다.
