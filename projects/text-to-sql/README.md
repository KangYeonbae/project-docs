## 어떤 문제였나

분석가가 아닌 사람도 데이터를 물어볼 수 있어야 한다는 요구는 흔합니다. 문제는 **"물어볼 수 있다"와 "믿을 수 있는 답이 온다" 사이의 거리**입니다.

자연어를 SQL로 바꾸는 것 자체는 모델이 잘합니다. 그런데 실제로 붙이려면 세 가지를 통제해야 합니다.

1. **스키마 추측** — 모델이 존재하지 않는 컬럼명을 지어냅니다
2. **잘못된 SQL** — 문법은 맞는데 의미가 틀린 쿼리가 나옵니다
3. **스캔 비용** — GA4 BigQuery는 파티션 필터 없이 돌리면 요금이 폭발합니다

여기에 하나 더. **실행이 실패했을 때 사용자에게 에러 메시지를 그대로 보여주면** 비전문가에게는 아무 의미가 없습니다.

## 어떻게 풀었나

질문에서 인사이트까지를 여섯 단계로 나누고, **생성과 실행 사이에 안전 경계**를 두었습니다.

```
질문 → 스키마 컨텍스트 + RAG → SQL 생성 → 안전 게이트 → BigQuery 실행 → 인사이트
                                                ↓ 실패 시
                                          Recovery (최대 2회)
```

**SQL 예시를 RAG로 재사용했습니다.** 다국어 임베딩과 키워드 부스트로 유사 SQL을 찾고, 실제 테이블 스키마와 함께 생성 모델에 전달합니다. 비슷한 질문이 반복될수록 정확도가 올라가고 생성 비용이 내려갑니다.

**안전 게이트는 화이트리스트 방식입니다.** `SELECT`와 `WITH`만 허용하고 `DROP`·`DELETE`·`ALTER` 등을 차단합니다. 여기에 더해 GA4 파티션 필터와 스키마를 검증한 SQL만 BigQuery로 보냅니다. 블랙리스트로 위험한 키워드를 막는 방식은 우회를 전부 예상해야 하지만, 화이트리스트는 허용한 것만 통과합니다.

**실패를 자동 복구합니다.** 실행 오류가 나면 원본 SQL·오류 메시지·질문을 Recovery 도구에 전달해 **최대 2회** 수정 실행합니다. 사용자는 에러 대신 결과를 받거나, 최소한 사람이 읽을 수 있는 설명을 받습니다.

## 결과

| 항목 | 내용 |
|---|---|
| 실행 제약 | `SELECT` / `WITH` 만 허용 |
| 오류 복구 | 최대 2회 자동 재시도 |
| 진행 표시 | SSE로 생성·실행·분석 단계 전달 |
| 탐색 깊이 | 복잡한 질문은 최대 3단계로 분해 |
| 캐시 | 반복 질의에 대한 쿼리 캐시 |

여러 GCP 프로젝트와 다중 테이블을 지원하고, 생성·실행·분석 단계를 SSE로 전달합니다.

## 이 프로젝트에서 배운 것

**Text-to-SQL의 어려움은 SQL 생성이 아니라 실행 경계 설계에 있었습니다.** 모델은 그럴듯한 쿼리를 잘 만듭니다. 문제는 그 쿼리가 데이터를 망가뜨리거나, 요금을 태우거나, 조용히 틀린 답을 줄 수 있다는 것입니다.

**같은 문제를 두 가지 오케스트레이션으로 만들어 비교했습니다.** 명시적 Handler Chain과 Google ADK의 Root·Query·Exploration Agent 구조를 **같은 UI에서 전환**할 수 있게 만들어, 단일 질의와 다단계 탐색에 각각 어느 쪽이 맞는지 확인했습니다.
