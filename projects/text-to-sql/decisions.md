## 01. SQL 예시를 RAG로 재사용했습니다

**검토했던 것**
스키마만 프롬프트에 넣고 모델이 SQL을 생성하게 하는 방식이 기본입니다. 구현이 단순합니다.

**부딪힌 문제**
스키마는 컬럼이 무엇인지 알려주지만 **그 조직에서 그 지표를 어떻게 계산하는지는 알려주지 않습니다.** 같은 "전환율"도 정의가 조직마다 다릅니다. 모델은 일반적인 방식으로 계산하고, 그건 그 조직의 기준과 다를 수 있습니다.

**결정**
과거 SQL 예시를 임베딩해 두고 질문과 유사한 것을 검색해 스키마와 함께 전달합니다. 검색은 **다국어 임베딩 + 키워드 부스트** 조합입니다.

- 다국어 임베딩 — 질문은 한국어, SQL 주석과 테이블명은 영어인 환경
- 키워드 부스트 — 임베딩만으로는 특정 지표명·테이블명 매칭이 약함

> **정리한 것** — 문맥 정확도와 반복 비용을 함께 개선했습니다. 같은 유형의 질문이 반복될수록 좋아지는 구조입니다.

## 02. 생성과 실행 사이에 안전 경계를 두었습니다

**검토했던 것**
생성된 SQL을 그대로 실행하고 오류가 나면 처리하는 방식. 대부분의 Text-to-SQL 데모가 이렇게 동작합니다.

**부딪힌 문제**
데모와 실제 환경의 차이가 여기서 갈립니다. 실제 BigQuery에 붙으면 두 가지 위험이 생깁니다.

1. **데이터 변경** — 모델이 `DELETE`나 `DROP`을 생성할 수 있습니다. 의도적이지 않아도 가능합니다
2. **스캔 비용** — GA4 이벤트 테이블을 파티션 필터 없이 쿼리하면 전체 기간을 스캔합니다. 한 번의 실수가 곧바로 요금입니다

**결정**
`SELECT`·`WITH`만 허용하는 **화이트리스트**로 막고, GA4 파티션 필터와 스키마를 검증한 SQL만 BigQuery로 보냅니다.

블랙리스트가 아니라 화이트리스트를 택한 이유는, 블랙리스트는 위험한 구문을 전부 예상해야 하고 하나라도 빠지면 뚫리기 때문입니다.

> **정리한 것** — 생성형 시스템을 실제 데이터에 붙일 때 필요한 건 더 좋은 프롬프트가 아니라 실행 경계입니다.

## 03. 실패를 자동 복구하되 횟수를 제한했습니다

**검토했던 것**
실행 오류를 사용자에게 그대로 보여주는 방식. 또는 무한 재시도.

**부딪힌 문제**
이 도구의 사용자는 분석가가 아닙니다. `Column name X is ambiguous` 같은 메시지는 그들에게 아무 의미가 없습니다. 반대로 무한 재시도는 비용이 통제되지 않습니다.

**결정**
실행 오류가 나면 **원본 SQL · 오류 메시지 · 원래 질문**을 Recovery 도구에 전달해 **최대 2회** 수정 실행합니다.

두 번 고쳐서 안 되는 쿼리는 대개 질문 자체가 그 데이터로 답할 수 없는 것입니다. 그 경우 계속 시도하기보다 왜 안 되는지 설명하는 편이 낫습니다.

> **정리한 것** — 자동 복구의 가치는 무한한 재시도가 아니라, 사용자가 이해할 수 없는 실패를 이해할 수 있는 결과로 바꾸는 데 있습니다.

## 04. 두 오케스트레이션을 같은 UI에서 비교했습니다

**검토했던 것**
명시적 Handler Chain과 Google ADK의 Root·Query·Exploration Agent 구조. 둘 중 하나를 고르는 것이 일반적입니다.

**부딪힌 문제**
문서와 벤치마크로는 어느 쪽이 이 문제에 맞는지 알 수 없었습니다. 단일 질의와 다단계 탐색은 요구가 다른데, 하나를 골라 구현하면 다른 쪽을 평가할 근거가 사라집니다.

**결정**
둘 다 구현하고 **같은 UI에서 전환**할 수 있게 만들어 직접 비교했습니다.

| 방식 | 특성 |
|---|---|
| Handler Chain | 경로가 고정이라 재현과 디버깅이 쉬움. 단일 질의에 적합 |
| ADK Agent 구조 | 질문이 열려 있을 때 탐색 경로를 스스로 확장. 다단계 탐색에 적합 |

> **정리한 것** — 선택지가 둘인데 판단 근거가 없으면, 고르기 전에 비교 가능한 상태를 만드는 것이 빠릅니다.
