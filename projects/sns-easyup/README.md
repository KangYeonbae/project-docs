## 확인하려던 것

SNS 운영은 도구가 흩어져 있습니다.

```
메모 앱에 아이디어  →  ChatGPT로 문구  →  이미지 생성 도구
                    →  각 채널 관리자 페이지에서 예약 발행
```

각 단계에서 복사·붙여넣기가 일어나고, 채널이 늘면 마지막 단계가 배로 늘어납니다.

**이걸 하나의 흐름으로 묶으면 실제로 편해지는가?** 그리고 채널마다 다른 인증·게시 규격을 어떻게 흡수해야 하는가. 이 두 가지를 확인하려고 만들었습니다.

## 어떻게 만들었나

### 프롬프트를 코드가 아니라 콘텐츠로

플랫폼과 길이별로 문구 스타일이 다릅니다. Instagram과 Facebook은 같은 내용이라도 어투와 길이가 달라야 합니다.

이걸 코드에 박으면 문구를 조정할 때마다 배포해야 합니다. **교체 가능한 레지스트리로 분리**하고 버전을 기록했습니다.

프롬프트는 계속 손보게 되는 대상입니다. 배포 없이 바꿀 수 있어야 실험이 됩니다. [Byeoljari에서 가격을 DB로 뺀 것](../byeoljari/decisions.md#03-가격을-코드가-아니라-db에-두었습니다)과 같은 판단입니다.

### 채널 어댑터

Facebook과 Instagram은 같은 Meta 플랫폼인데도 인증 방식과 게시 규격이 다릅니다. 이미지 요구사항, 캡션 길이 제한, 예약 발행 지원 여부가 각각입니다.

**이 차이를 공통 작성 흐름 밖으로 격리**했습니다. 사용자는 하나의 편집 화면에서 작업하고, 어댑터가 각 채널의 규격으로 변환합니다.

채널을 추가할 때 어댑터만 쓰면 되는 구조를 목표로 했습니다.

### BYO API 키

사용자가 자기 API 키를 넣어 쓰는 구조입니다. 실험 단계에서 생성 비용을 서비스가 부담할 이유가 없고, 사용자 입장에서도 자기 키를 쓰면 사용량과 비용이 투명합니다.

### 예약 발행과 복구

예약 시각에 발행하려면 스케줄러가 필요합니다. Cron으로 큐를 확인해 발행하고, 실패한 건은 다시 시도합니다.

## 결과

| 영역 | 구현 |
|---|---|
| 입력 | 아이디어 · 에셋 |
| 프롬프트 | 버전 관리되는 레지스트리 |

| 예약 | 스케줄 큐 + Cron 복구 |

## 확인한 것과 남은 것

**확인한 것.** 아이디어에서 발행까지 한 흐름으로 묶는 것은 동작합니다. 특히 채널 어댑터로 규격 차이를 격리하니, 작성 화면은 채널 수와 무관하게 단순하게 유지됐습니다.

**남은 것.** 생성 품질이 채널 특성을 충분히 반영하는지는 더 검증이 필요합니다. 프롬프트 레지스트리는 구조를 만들었지만, 어떤 프롬프트가 좋은지는 별개의 문제입니다.

**Lab으로 분류한 이유.** 운영 중인 서비스가 아니라 구조를 검증한 실험입니다. 실제 사용자 규모에서의 API 제한, 계정 정지 리스크, 발행 실패율 같은 것은 다루지 않았습니다.
