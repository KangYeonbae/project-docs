# GA4 Event Validator

> 화면이 정상 동작하는 것과 계측이 정상 동작하는 것은 다른 문제입니다.

|  |  |
|---|---|
| **기간** | 2025.09 |
| **역할** | Automation · Data QA |
| **상태** | 완료 |
| **스택** | Playwright · Python · AsyncIO · GA4 · dataLayer |

📄 [시스템 구조](architecture.md)

---

## 어떤 문제였나

GA4 계측은 조용히 깨집니다.

버튼을 누르면 화면은 정상적으로 동작합니다. 다음 페이지로 넘어가고, 장바구니에 담기고, 결제가 됩니다. **그런데 그 시점에 전송돼야 할 이벤트가 누락되거나, 필수 파라미터가 빠진 채로 나갈 수 있습니다.**

이걸 사람이 확인하려면 개발자 도구를 열고 플로우를 하나씩 밟으면서 `dataLayer`를 눈으로 봐야 합니다. 화면이 많아지면 현실적으로 불가능하고, 배포할 때마다 반복해야 합니다.

문제가 드러나는 시점은 대개 **한참 뒤**입니다. 데이터를 분석하려고 보니 특정 기간의 이벤트가 없는 걸 발견하는 식입니다. 그때는 이미 그 기간의 데이터를 복구할 수 없습니다.

## 어떻게 풀었나

### UI 성공과 계측 성공을 분리해서 기록

버튼 클릭이 끝났다는 사실만 확인하지 않습니다. **같은 시점의 `dataLayer` 이벤트 이름과 필수 파라미터를 별도 결과로 기록**합니다.

```
클릭 실행 → [UI 결과: 성공]
          → [계측 결과: purchase 이벤트 누락]  ← 별도 판정
```

두 결과를 나누니 "화면은 되는데 계측이 안 되는" 상태가 그대로 보입니다.

### 재현 가능한 시나리오

탐색 순서와 대기 조건을 **코드로 고정**했습니다. 담당자가 다르거나 실행 시점이 달라도 같은 계측 경로를 지나갑니다.

수동 확인의 가장 큰 문제는 매번 다른 경로를 밟는다는 것입니다. 이번엔 상품 A를, 다음엔 상품 B를 눌러보면 결과를 비교할 수 없습니다.

### 원본 이벤트를 증거로 남김

판정 결과만 저장하지 않고 **관측된 원본 이벤트를 함께 기록**합니다. "누락됨"이라는 결론만 있으면 왜 그렇게 판정했는지 확인할 수 없고, 판정 로직이 틀렸을 가능성도 배제할 수 없습니다.

## 결과

| 항목 | 내용 |
|---|---|
| 실행 | 비동기 시나리오 (AsyncIO) |
| 판정 | 규칙 기반 이벤트 매칭 |
| 증거 | 원본 이벤트 로그 보존 |
| 재현성 | 코드로 고정된 탐색 경로 |

대상은 모바일 웹의 사용자 플로우였습니다.

## 이 프로젝트의 배경

이 도구는 [Local Browser Agent](../local-browser-agent/)의 확장에서 갈라져 나왔습니다.

자율 탐색 에이전트로 `dataLayer`를 수집해 본 결과, 커버리지는 넓힐 수 있지만 **매번 다른 경로를 타서 결과를 비교할 수 없다**는 한계가 있었습니다. 회귀 검증에는 재현성이 필요합니다.

| 접근 | 강점 | 약점 |
|---|---|---|
| 자율 탐색 (Local Browser Agent) | 커버리지 확장 | 실행마다 경로가 다름 |
| 고정 시나리오 (이 도구) | 재현·비교 가능 | 정의한 경로만 검증 |

두 방식을 모두 만들어 보고 나서야 각각의 쓰임이 명확해졌습니다.

---

## 이 프로젝트에서 배운 것

**"동작한다"의 정의를 나눠야 하는 영역이 있습니다.** UI 테스트는 화면이 되는지 보고, 계측 테스트는 데이터가 나가는지 봅니다. 하나로 합치면 둘 중 하나가 가려집니다.

**판정에는 증거가 따라야 합니다.** 자동 판정 도구를 신뢰하려면 판정 근거를 볼 수 있어야 합니다. 이건 [Amazon Ads Agent에서 리포트에 근거 표를 함께 실은 것](../amazon-ads-agent/operations.md#사람이-개입할-지점을-남겨-두었습니다)과 같은 판단입니다.
