## 어떤 문제였나

학교급식에 식자재를 납품하려면 전자조달 시스템에 올라오는 입찰 공고를 보고 참여합니다. 공고에는 그 학교가 어떤 품목을 얼마나 사려는지가 첨부파일로 붙습니다.

납품업체 입장에서 판단해야 할 것은 하나입니다. **이 공고가 우리가 취급하는 품목이고, 남는 장사인가.**

그런데 그 판단이 어려웠습니다.

- 공고 수가 많고, 대부분 매월 20일 전후 **5~6일에 몰립니다**
- 첨부 현품설명서는 학교가 직접 만들어 올려서 **양식이 제각각**입니다
- 같은 식재료를 학교마다 다르게 표기해 비교가 안 됩니다
- 수익성 계산(하한가, 예상이익)을 엑셀로 직접 해야 합니다

결과적으로 **공고를 검토하는 데만 3~4시간**이 걸렸고, 그것도 시즌에 몰려서 걸렸습니다.

## 어떻게 풀었나

### 수집 — 화면이 아니라 계약을 다룬다

대상 조달 시스템은 Nexacro 기반 SPA라 HTML 소스에 데이터가 없습니다. 그래서 처음에는 Playwright로 브라우저를 띄워 조작했습니다.

동작은 했지만 화면 DOM 변경에 취약했고, Cloud Run Job에서 브라우저를 띄우는 비용이 컸습니다. 조작 과정에서 **XHR을 관찰해 요청 스펙을 역설계**하고, 목록·상세·첨부 3개 API를 직접 호출하는 순수 `requests` 파이프라인으로 전환했습니다.

브라우저가 사라지자 실행이 가벼워졌고, XML 컬럼 ID 기반 파싱이라 화면이 바뀌어도 영향받지 않게 됐습니다.

### 해석 — 분기 기준은 사이트가 아니라 공고다

공고마다 품목 정보가 오는 방식이 다릅니다. 어떤 공고는 시스템에 구조화된 데이터로 올라오고, 어떤 공고는 엑셀 첨부에만 있습니다. **로그를 보면 8건 중 6건이 첨부 경로**였습니다.

첨부 경로는 규칙 기반 pandas 파서가 먼저 처리합니다. 헤더행 자동 탐색 → 컬럼명 매핑 → 인덱스 컬럼 판별 순으로 시도하고, **모두 실패할 때만 Gemini로 넘깁니다.** LLM을 기본 경로가 아니라 마지막 폴백에 둔 이유는 비용과 재현성입니다.

### 판단 — 계산을 사용자보다 앞에 둔다

하한가(단가 × 사정률)와 예상이익(하한가 합계 − 내물품가)을 자동 계산합니다. 이 계산을 **목록 조회 시점이 아니라 수집 저장 직후**에 미리 해둡니다. 사용자가 몰리는 시점과 계산이 가능한 시점이 다르기 때문입니다.

## 규모

운영 DB 덤프 실측 · 2026.03.06 기준

| 지표 | 값 | 비고 |
|---|---|---|
| 실사용 소요시간 | **3~4시간 → 30분** | 현업 사용자 기준 · 약 85% 단축 |
| 누적 수집 공고 | **877건** | 일 자동 수집 |
| 누적 품목 | **29,761행** | 공고당 평균 34행 |
| 정규화 품목 코드 | **9,521개** | 대분류 4 · 중분류 59 · 품목그룹 4,229 |
| 학교 마스터 | **1,416개교** | 묶음입찰 개별학교 306행 |
| 첨부파일 파싱 | **1,608건** | 엑셀 자동 파서 + LLM 폴백 |

수집 대상은 학교급식 전자조달 시스템 1곳이고, 역설계한 API 엔드포인트는 목록·상세·첨부 3종입니다. 지역코드 250개를 파싱해 보유하되 운영은 서울·경기 2개 지역 × 축산 3개 키워드, 하루 6조합으로 좁혀 실행합니다.

## 결과

**업무** — 매월 20일 전후 5~6일에 물량이 몰리는 업무입니다. 엑셀로 3~4시간 걸리던 공고 검토가 **30분 내외**로 줄었습니다.

**자동화 범위** — 수집(자정 자동 실행) · 매칭(저장 직후 사전 계산) · 판단(하한가·예상이익 계산) 세 단계에서 수작업을 제거했습니다.

**데이터 자산** — 공고를 모으는 데서 끝내지 않고 **9,521개 표준 식품코드로 정규화**해, 품목·단가를 누적 비교할 수 있는 DB를 만들었습니다. 이건 서비스가 오래 돌수록 가치가 커지는 자산입니다.

## 이 프로젝트에서 배운 것

**자동화 도구를 고르는 문제가 아니었습니다.** 조작해야 할 화면을 관측 가능한 계약으로 바꾸는 문제였습니다. Playwright에서 API 직접 호출로 옮긴 것이 이 프로젝트에서 가장 큰 구조 변경이었습니다.

**깨지는 쪽은 항상 예상과 달랐습니다.** 사이트 구조가 바뀔 것을 걱정했는데, 실제로 계속 깨진 건 학교가 직접 올린 엑셀이었습니다.

**자동화 실패를 사용자 참여형 데이터로 바꿀 수 있습니다.** 한글 파일로 오는 정보는 자동 추출이 불가능했습니다. 완전 자동화를 고집하는 대신, 사용자가 한 번 체크하면 다음부터 표시되는 토글로 만들었습니다. 한 번의 입력이 다음 사용자에게 남습니다.
