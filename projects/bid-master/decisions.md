## 01. 브라우저 자동화에서 API 직접 호출로 전환했습니다

**검토했던 것**
대상이 Nexacro 기반 SPA라 HTML 소스에 데이터가 없었습니다. HTML 파서로는 **파싱할 대상 자체가 없어** 후보에서 먼저 제외했습니다.

**부딪힌 문제**
그래서 Playwright로 브라우저를 띄워 클릭 가능 요소를 스캔하고 좌표를 매핑(Set-of-Mark)해 조작했습니다. 동작은 했지만 두 가지 비용이 있었습니다.

- 화면 DOM이 바뀌면 깨집니다
- Cloud Run Job에서 브라우저를 기동하는 비용이 큽니다

**결정**
조작 과정에서 XHR을 관찰해 **Nexacro XML 요청 스펙을 역설계**하고, 목록·상세·첨부 3개 API를 직접 호출하는 순수 `requests` 파이프라인으로 전환했습니다.

**얻은 것**
브라우저 기동이 사라져 Cloud Run Job(2Gi, asia-northeast3)에서 안정적으로 돌고, XML 컬럼 ID 기반 파싱이라 화면 변경에 둔감해졌습니다.

**남은 부채**
Dockerfile에 chromium 설치가 남아 이미지가 불필요하게 큽니다. 전환은 마쳤지만 정리하지 못한 부채로 인지하고 있습니다.

> **정리한 것** — 자동화 도구를 고르는 문제가 아니라, 조작해야 할 화면을 관측 가능한 계약으로 바꾸는 문제였습니다.

## 02. 매칭을 조회 시점이 아니라 저장 직후에 계산했습니다

**검토했던 것**
목록을 열 때 사용자별 수익성을 실시간으로 계산하는 방식이 기본 선택지였습니다. 구현이 단순하고, 사용자 설정이 바뀌면 즉시 반영됩니다.

**부딪힌 문제**
입찰 시즌이 **매월 20일 전후 5~6일에 몰립니다.** 사용자가 가장 몰리는 시점에 가장 무거운 계산이 겹치는 구조였습니다. 평소에는 한가하고 시즌에만 터지는 형태라 부하 테스트로도 잘 드러나지 않습니다.

**결정**
수집 저장 직후 `calculate-matches`를 **50건 배치**로 트리거해 `user_tender_matches` 캐시에 미리 계산해 두고, 목록 조회는 캐시만 읽도록 분리했습니다.

> **정리한 것** — 사용자가 몰리는 시점과 계산이 가능한 시점이 다르면, 계산을 앞으로 당깁니다.

## 03. 자동화가 불가능한 지점은 사용자 참여로 바꿨습니다

**검토했던 것**
G마크를 요구하는 학교는 해당 정보가 엑셀이 아니라 한글 파일로 오는 경우가 있어 **자동 추출이 불가능**했습니다.

**부딪힌 문제**
완전 자동화를 고집하면 그 학교들은 시스템이 아예 다룰 수 없게 됩니다. 그러면 사용자는 그 부분만 다시 수작업으로 돌아가고, 결국 두 벌의 작업이 생깁니다.

**결정**
자동 추출을 포기하고, **사용자가 한 번 체크하면 다음부터 배지로 표시되는 토글**로 바꿨습니다. 단가 DB와 공유 단가 DB도 같은 방식으로 설계했습니다.

> **정리한 것** — 자동화 실패를 사용자 참여형 데이터 자산으로 바꿨습니다. 한 번의 입력이 다음 사용자에게 남습니다.

## 04. LLM을 기본 경로가 아니라 마지막 폴백에 두었습니다

**검토했던 것**
첨부 엑셀의 양식이 제각각이라, 처음부터 LLM에 파일을 넘겨 품목을 추출하게 하는 방식이 가장 간단했습니다. 규칙을 짤 필요가 없습니다.

**부딪힌 문제**
누적 **1,608건**을 처리하는 경로입니다. 매 건 모델을 호출하면 비용이 계속 발생하고, 같은 파일에 다른 결과가 나올 수 있습니다. 파싱 결과가 곧 수익성 계산의 입력이라 재현성이 중요했습니다.

**결정**
규칙 기반 pandas 파서를 3단계로 두고(헤더행 자동 탐색 → 컬럼명 매핑 → 인덱스 컬럼 판별), **전부 실패할 때만** Gemini로 넘깁니다.

> **정리한 것** — LLM은 규칙이 감당하지 못하는 꼬리를 처리할 때 가장 값어치가 있습니다. 몸통까지 맡기면 비용과 재현성을 함께 잃습니다.

## 남은 과제

- **Dockerfile chromium 잔존** — API 전환 후 정리하지 못한 부채
