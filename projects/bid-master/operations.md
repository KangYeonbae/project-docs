## 가장 오래 붙잡은 문제 — 학교마다 제각각인 엑셀 양식

시작할 때는 **사이트 구조가 바뀌는 것**을 가장 큰 리스크로 봤습니다. 크롤링 시스템의 전형적인 실패 지점이니까요.

실제로는 아니었습니다. API 경로는 XML 컬럼 ID 기반이라 화면 변경에 둔감했고, **깨지는 쪽은 항상 학교가 직접 올린 엑셀**이었습니다. 표준 양식이 없으니 매번 다른 방식으로 깨졌습니다.

### 실제 장애 — 다중 시트 공고

**증상**
한 학교가 농산·축산·수산을 시트로 나눠 올린 공고에서, 파서가 **전체 시트를 읽었습니다.** 축산만 취급하는 사용자에게 농산·수산 품목까지 포함된 계산이 나갔고, 매칭률과 예상 금액이 함께 왜곡됐습니다.

파싱은 성공했고 에러도 없었습니다. 숫자가 조용히 틀린 유형입니다.

**대응**
두 가지를 했습니다.

1. **키워드와 시트명을 매칭**해 대상 시트만 파싱하고, 매칭되는 시트가 없으면 전체로 폴백
2. **실제로 읽은 시트명을 UI에 노출**

두 번째가 더 중요합니다. 자동 판별은 언제든 틀릴 수 있는데, 무엇을 읽었는지 보이면 사용자가 이상을 발견할 수 있습니다. **완전 자동화 대신 관측 가능성으로 신뢰를 확보한 경우**입니다.

### 파싱 전략

```
1. 헤더행 자동 탐색
2. 컬럼명 매핑
3. 인덱스 컬럼 판별
   ↓ 모두 실패할 때만
4. Gemini 폴백
```

LLM을 기본 경로가 아니라 마지막 폴백에 둔 이유는 비용과 재현성입니다. 자세한 판단은 [설계 판단 04](decisions.md#04-llm을-기본-경로가-아니라-마지막-폴백에-두었습니다)에 있습니다.

## 중복 · 재실행 · 유실 방어

지역별로 순회하는 구조라 같은 공고가 여러 번 수집됩니다. 중복 제거와 재실행 안전성을 계층으로 나눠 처리했습니다.

| 계층 | 방식 |
|---|---|
| `etn_bid_id` 인메모리 dedup | 1차 |
| `bid_number` UNIQUE + upsert | 멱등 |
| 기수집 공고 상세조회 스킵 | LLM 비용 절감 |
| 네트워크 오류만 선별 백오프 | 5 → 10 → 20초 |
| 시작 전 DB 연결 확인 | 5회 |

마지막 항목의 이유를 적어 둡니다. **저장이 불가능한 상태에서 크롤링하면 수집한 데이터가 그대로 유실됩니다.** 크롤링은 성공했는데 저장에서 전부 날아가면, 다음 실행까지 하루를 잃습니다. 그래서 크롤링을 시작하기 전에 DB 연결을 백오프로 확인하고, 실패하면 아예 시작하지 않습니다.

**남은 과제** — 엑셀 경로로 들어온 품목의 `school_id`가 NULL로 남는 케이스가 있습니다. `tender_schools`가 API 품목 경로에서만 insert되는 구조가 원인입니다.

## 협업 — 증상을 수용 기준으로 번역하기

기획을 클라이언트가 맡은 프로젝트였습니다. 요구는 대부분 **증상으로 전달됐고**, 제 역할은 그것을 가설과 수용 기준으로 번역하는 것이었습니다.

증상을 그대로 고치면 다음 증상이 또 옵니다. 무엇이 고쳐진 상태인지 정의하지 않으면 "고쳤다"고 말할 수도 없습니다.

### 사례 1 — 재현 조건이 애매한 버그

**받은 증상**
"학교를 6번째 연속으로 클릭하면 데이터가 안 나옵니다."

**번역**
가설을 다섯 갈래로 나눴습니다 — 요청 레이스 컨디션 · 세션 만료 · 요청 취소 미처리 · 429 · 전역 상태 덮어쓰기.

수용 기준은 이렇게 합의했습니다.

- "20회 연속 클릭에도 미재현"
- "빈 화면 대신 재시도·원인 메시지·자동 재요청 중 최소 하나는 동작"

두 번째 기준이 중요합니다. 원인을 전부 제거하지 못하더라도 **사용자가 빈 화면을 보지 않는 것**은 보장할 수 있습니다.

### 사례 2 — 간헐적 상태 소실

**받은 증상**
"뒤로 가면 데이터가 없어집니다. 될 때도 있고 안 될 때도 있고요."

**번역**
상태 소실로 가설을 세우고, 수용 기준을 문서화했습니다.

- 검색어·필터·스크롤 위치·결과 리스트 **100% 복구**
- 브라우저 뒤로가기와 앱 내 뒤로가기 **동일 동작**

### 사례 3 — 요구가 기술적으로 불가능한 경우

**받은 요구**
"축산 시트만 읽어주세요."

**번역**
첨부 구조상 사용자가 시트를 고를 수 없는 케이스가 있었습니다. 요구를 그대로 구현할 수 없다는 사실을 먼저 설명하고, **자동 판별 규칙을 적용하되 현재 읽은 시트명을 화면에 표시**하는 것으로 합의했습니다.

### 우선순위를 근거를 갖고 합의했습니다

클라이언트가 "안정성만 잡히면 유료로 쓰겠다"고 말한 것을 근거로, 신규 기능보다 **P0 안정성 버그를 먼저** 처리하기로 정했습니다.

실제로 P0 8건을 끝낸 뒤 기능 6건 순서로 진행했습니다. 순서를 감이 아니라 상대가 말한 조건에서 끌어낸 것이 이 합의의 핵심입니다.
