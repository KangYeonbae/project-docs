## 어떤 문제였나

여러 언어로 콘텐츠를 운영하는 조직에서, 일반적인 CMS의 데이터 모델은 이렇습니다.

```
Post {
  title, content, published: boolean
}
```

번역이 붙으면 이렇게 확장합니다.

```
Post {
  published: boolean
  translations: [{ locale, title, content }]
}
```

**여기서 문제가 생깁니다.** 한국어 원문은 발행됐고, 영어는 번역 검수 중이고, 일본어는 아직 번역도 시작하지 않았다면 — 이 게시물의 `published`는 무엇이어야 합니까?

`true`로 두면 번역이 준비되지 않은 언어에서 빈 페이지나 원문이 노출됩니다. `false`로 두면 이미 준비된 한국어까지 막힙니다.

실제 운영에서는 **언어마다 번역·검수·발행 시점이 다릅니다.** 모델이 그 현실을 표현하지 못하면, 운영자는 시스템 밖에서 스프레드시트로 상태를 관리하게 됩니다.

## 어떻게 풀었나

### 언어별 상태 머신

게시물 전체가 아니라 **각 언어 버전이 독립적인 상태**를 갖도록 모델링했습니다.

```
draft → review → published
```

각 로케일이 이 상태를 따로 가집니다. 한국어가 `published`인 동안 영어는 `review`, 일본어는 `draft`일 수 있습니다. 공개 페이지는 각 언어의 상태를 보고 노출 여부를 결정합니다.

### 편집기와 발행 결과 분리

Tiptap 편집 데이터와 공개 렌더 결과를 구분했습니다. 편집 중인 내용이 곧바로 공개 페이지에 반영되지 않고, **미리보기와 실제 발행의 경계**가 명확합니다.

### SEO 구조화 데이터

다국어 콘텐츠는 검색엔진에 언어 관계를 알려줘야 합니다. JSON-LD 구조화 데이터와 언어 대체 링크를 발행 시점에 생성합니다.

## 결과

| 영역 | 내용 |
|---|---|
| 콘텐츠 상태 | 로케일별 독립 상태 머신 (draft / review / published) |
| 편집 | Tiptap 기반 리치 에디터 |
| 미디어 | 서명 URL 기반 접근 제어 |
| SEO | JSON-LD 구조화 데이터 · 언어 대체 링크 |
| 권한 | 역할 경계 분리 |

## 이 프로젝트에서 배운 것

**데이터 모델이 운영 현실을 표현하지 못하면, 운영은 시스템 밖으로 나갑니다.** `published: boolean` 하나로 다국어 상태를 담으려다 보면 결국 스프레드시트가 등장합니다. 모델을 현실에 맞추는 편이 빠릅니다.

**"번역"은 콘텐츠의 속성이 아니라 독립적인 작업 단위입니다.** 각 언어 버전은 자기 담당자, 자기 마감, 자기 검수 절차를 갖습니다. 부속 필드로 다루면 그 워크플로를 표현할 수 없습니다.
