## 어떤 문제였나

디지털 사이니지(DID)는 매장이나 시설에 설치된 디스플레이에 콘텐츠를 띄우는 시스템입니다. 관리자가 어떤 화면에 무엇을 언제 보여줄지 정하면, 각 단말이 그대로 재생합니다.

여기에 두 가지 제약이 붙었습니다.

### 폐쇄망

외부 인터넷이 제한된 환경이었습니다. 클라우드 스토리지도, 외부 CDN도, SaaS 서비스도 쓸 수 없습니다. **모든 구성 요소가 내부망 안에서 완결돼야 했습니다.**

### 대용량 미디어 + 잦은 상태 이벤트

성격이 정반대인 두 종류의 데이터를 다뤄야 했습니다.

| 데이터 | 특성 |
|---|---|
| 미디어 파일 | 크고, 자주 안 바뀌고, 전송에 시간이 걸림 |
| 단말 상태 | 작고, 계속 바뀌고, 즉시 반영돼야 함 |

이 둘을 같은 방식으로 다루면 양쪽 다 나빠집니다.

## 어떻게 풀었나

### 메타데이터와 파일을 분리

콘텐츠 정보는 **PostgreSQL**, 대용량 파일은 **MinIO**(S3 호환 오브젝트 스토리지)에 저장했습니다.

```
PostgreSQL          MinIO
├─ 콘텐츠 메타      ├─ 영상 파일
├─ 스케줄           ├─ 이미지 파일
└─ 단말 정보        └─ ...
```

**나눈 이유.**

- 백업 전략이 다릅니다. 메타데이터는 자주, 미디어는 드물게
- 전송 경계가 다릅니다. DB 쿼리는 가볍고, 파일 전송은 무겁습니다
- 파일을 DB에 넣으면 백업·복구·마이그레이션이 전부 무거워집니다

MinIO를 고른 것은 폐쇄망 조건 때문입니다. S3 호환 인터페이스를 쓰면서 **내부망에 직접 설치**할 수 있습니다.

### 상태 전달에 MQTT

단말의 연결 상태와 재생 명령은 **잦은 이벤트**입니다. HTTP 폴링으로 처리하면 단말 수에 비례해 요청이 늘고, 그러면서도 실시간성은 폴링 주기만큼 늦습니다.

**MQTT 브로커**를 두어 상태와 명령을 메시지로 주고받게 했습니다. 단말이 연결을 유지하고 있으므로 서버가 즉시 명령을 밀어넣을 수 있고, 연결이 끊기면 그 자체가 상태 정보가 됩니다.

## 이 프로젝트에서 배운 것

**제약이 아키텍처를 결정합니다.** 폐쇄망이라는 조건 하나가 스토리지·통신·배포 방식을 전부 규정했습니다. 클라우드를 쓸 수 있었다면 훨씬 단순했겠지만, 그럴 수 없는 환경이 존재하고 거기서도 시스템은 돌아가야 합니다.

**데이터의 성격이 다르면 전달 방식도 달라야 합니다.** 큰 파일과 잦은 이벤트를 같은 채널로 다루면 양쪽 다 나빠집니다. HTTP와 MQTT를 함께 쓴 것은 두 종류의 트래픽이 서로를 방해하지 않게 하기 위해서였습니다.
