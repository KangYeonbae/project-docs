## 어떤 문제였나

수학 문제를 데이터로 다루려고 하면 곧바로 벽에 부딪힙니다.

"다음 일차함수의 그래프에서 기울기를 구하시오"라는 문항이 있습니다. 여기서 **숫자 하나만 바꿔도** 함께 바뀌어야 하는 것들이 있습니다.

- 문제 본문의 수치
- **정답**
- 오답 선택지 4개 (정답과 헷갈릴 만한 값이어야 합니다)
- **그래프 도형** — 기울기가 바뀌면 그림이 달라집니다

문항을 텍스트로 저장하면 이 연동이 끊깁니다. 숫자를 바꾸면 정답이 틀리고, 그림은 그대로입니다. 결국 사람이 하나씩 다시 만들어야 하고, 그러면 문항 은행의 의미가 없습니다.

여기에 실무 요구가 하나 더 있습니다. **인쇄물은 A4 규격을 정확히 지켜야 합니다.** 화면에서 잘 보이는 것과 종이에 제대로 나오는 것은 다른 문제입니다.

## 어떻게 풀었나

### 문항을 데이터가 아니라 생성기로 모델링

문제 문장과 정답을 따로 저장하지 않습니다. **파라미터를 입력하면 모든 산출물이 함께 만들어지는 함수**로 문항을 정의했습니다.

```
파라미터 { 기울기: 2, 절편: -3 }
    ↓
├── 문제 본문
├── 정답
├── 선택지 4개
└── TikZ 도형
```

숫자를 바꾸면 전부 다시 계산됩니다. **불일치가 구조적으로 발생할 수 없습니다.**

### TikZ 렌더러를 격리

수학 도형은 TikZ로 그립니다. 정밀하고 인쇄 품질이 좋지만, **TeX 바이너리가 필요합니다.**

TeX가 설치된 환경을 일반 웹 앱과 같은 곳에 두면 배포가 무거워지고 보안 표면도 넓어집니다. 렌더링 작업을 **별도 서비스로 분리**하고, 서버 간 토큰으로 원시 TikZ API를 보호했습니다.

컴파일 결과는 SVG로 캐시합니다. 같은 파라미터면 다시 컴파일하지 않습니다.

### 도메인 검증을 빌드에 포함

타입 검사만으로는 잡을 수 없는 것들이 있습니다.

- 좌표가 의도한 사분면에 있는가
- 각도가 유효한 범위인가
- 편집 가능하다고 표시한 파라미터가 실제로 편집 가능한가

**수학 규칙 자체를 자동 검증**해 빌드에 포함했습니다. 타입이 맞아도 수학적으로 틀린 문항은 통과하지 못합니다.

## 결과

| 영역 | 구현 |
|---|---|
| 문항 정의 | 파라미터 기반 생성기 |

## 이 프로젝트에서 배운 것

**저장할 것과 계산할 것을 나누는 게 도메인 모델링입니다.** 정답을 저장하면 파라미터와 어긋날 수 있지만, 계산하면 어긋날 수 없습니다. 파생 가능한 값을 저장하지 않는 것이 정합성을 보장하는 가장 확실한 방법이었습니다.

**타입 시스템이 잡아주지 않는 규칙이 있습니다.** `angle: number`는 타입상 유효하지만 `-500도`는 수학적으로 무의미합니다. 도메인 규칙은 도메인 검증으로 따로 잡아야 합니다.

**인쇄는 별개의 출력 매체입니다.** 화면 레이아웃을 그대로 인쇄하면 대개 깨집니다. A4 규격을 지키는 것을 처음부터 요구사항으로 두고 설계했습니다.
