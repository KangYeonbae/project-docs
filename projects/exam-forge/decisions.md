## 01. 문항을 데이터가 아니라 생성기로 모델링했습니다

**검토했던 것**
문항을 레코드로 저장하는 방식입니다. 본문, 정답, 선택지, 이미지 URL을 필드로 두면 CRUD가 단순하고 검색도 쉽습니다.

**부딪힌 문제**
수학 문항은 **구성 요소가 서로 종속**되어 있습니다. 기울기를 2에서 3으로 바꾸면 본문의 수치, 정답, 선택지, 그래프 도형이 전부 바뀌어야 합니다.

레코드 방식에서는 이 연동을 사람이 지켜야 합니다. 하나라도 놓치면 틀린 문항이 되고, **틀렸다는 사실은 대개 인쇄한 뒤에 발견됩니다.**

**결정**
문제 문장과 정답을 따로 저장하지 않고, **같은 파라미터에서 모든 결과가 만들어지도록** 구성했습니다.

```
저장: { 기울기: 2, 절편: -3 } + 생성기 정의
계산: 본문 · 정답 · 선택지 · 도형
```

파생 가능한 값을 저장하지 않으므로 불일치가 구조적으로 발생할 수 없습니다.

> **정리한 것** — 저장할 것과 계산할 것을 나누는 게 도메인 모델링입니다. 정답을 저장하면 어긋날 수 있지만, 계산하면 어긋날 수 없습니다.

## 02. TikZ 렌더러를 격리했습니다

**검토했던 것**
웹 앱 안에서 TikZ를 컴파일하는 방식. 배포 단위가 하나라 단순합니다.

**부딪힌 문제**
세 가지가 걸렸습니다.

| 문제 | 내용 |
|---|---|
| 배포 무게 | TeX 배포판은 큽니다. 웹 앱 이미지에 넣으면 빌드·배포가 느려집니다 |
| 보안 | TeX는 강력한 매크로 언어입니다. 임의 입력을 컴파일하는 것은 위험합니다 |
| 리소스 특성 | 컴파일은 CPU 바운드 작업이라 웹 요청 처리와 프로파일이 다릅니다 |

**결정**
TeX 바이너리가 필요한 컴파일 작업을 **별도 서비스로 분리**하고, **서버 간 Bearer 토큰**으로 원시 TikZ API를 보호했습니다. 브라우저에서 직접 임의의 TikZ를 컴파일 요청할 수 없습니다.

컴파일 결과는 SVG로 캐시해, 같은 파라미터면 다시 컴파일하지 않습니다.

> **정리한 것** — 실행 특성과 신뢰 경계가 다른 코드는 배포 단위를 나눕니다. 편의를 위해 합치면 보안과 성능을 함께 잃습니다.

## 03. 도메인 검증을 빌드에 포함했습니다

**검토했던 것**
TypeScript 타입 검사로 충분하다고 볼 수도 있었습니다. 파라미터 타입을 정의하면 잘못된 값이 들어가는 것은 막힙니다.

**부딪힌 문제**
**타입이 맞아도 수학적으로 틀린 문항**이 만들어질 수 있습니다.

```typescript
angle: number   // 타입상 유효
angle = -500    // 수학적으로 무의미
```

좌표가 의도한 사분면을 벗어나거나, 각도가 도형을 성립시키지 못하거나, 편집 가능하다고 표시한 파라미터가 실제로는 다른 값을 깨뜨리는 경우가 있었습니다.

**결정**
타입 검사 외에 **사분면·각도·편집 가능 파라미터 등 수학 규칙을 자동 검증**하고, 이 검증을 빌드에 포함했습니다. 규칙을 위반한 문항 정의는 배포되지 않습니다.

> **정리한 것** — 타입 시스템은 값의 형태를 보장하지 의미를 보장하지 않습니다. 도메인 규칙은 도메인 검증으로 따로 잡아야 합니다.

## 04. A4 지면을 나중이 아니라 처음부터 기준으로 잡았습니다

**검토했던 것**
화면용 레이아웃을 먼저 만들고 인쇄 CSS를 나중에 얹는 일반적인 순서입니다.

**부딪힌 문제**
시험지는 **종이로 출력되는 것이 최종 형태**입니다. 화면에서 잘 보이던 것이 인쇄하면 여백이 어긋나거나 문항이 페이지 경계에서 잘립니다. 나중에 고치려면 레이아웃을 다시 짜야 합니다.

**결정**
편집기가 처음부터 **A4 지면을 기준 단위로** 동작하도록 만들었습니다. 화면은 지면을 보여주는 뷰이지 별도의 레이아웃이 아닙니다.

> **정리한 것** — 최종 출력 매체가 화면이 아니면, 화면 기준으로 설계하면 안 됩니다.
