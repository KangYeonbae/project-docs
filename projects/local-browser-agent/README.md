# Local Browser Agent

> 고객 화면을 외부 AI API로 보내지 않으면서, 자연어 목표를 이해하고 웹사이트를 자율 조작합니다.

|  |  |
|---|---|
| **기간** | 2025.10 |
| **역할** | AI Agent · Browser Automation / 단독 개발 |
| **상태** | 프로토타입 |
| **스택** | Ollama · LangGraph · Qwen2.5 · LLaVA · Playwright |

📄 [시스템 구조](architecture.md) · [설계 판단](decisions.md)

## 어떤 문제였나

브라우저를 자동 조작하는 에이전트는 화면을 봐야 합니다. 화면을 보려면 스크린샷을 모델에 넘겨야 하고, 상용 멀티모달 API를 쓰면 그 스크린샷이 **외부로 나갑니다.**

고객사 사이트를 다루는 작업에서는 이게 그대로 제약이 됩니다. 로그인 후 화면, 주문 내역, 내부 관리 도구가 찍힌 이미지를 외부 API로 보내는 것에 동의를 받기 어렵습니다.

동시에 자동화 자체의 난이도도 있었습니다.

- 사이트마다 UI가 다릅니다. 셀렉터를 미리 정할 수 없습니다
- DOM만 보면 시각적으로 어떤 요소가 실제로 클릭 가능한지 알기 어렵습니다
- 스크린샷만 보면 모델이 좌표를 추측해야 하고, 대개 틀립니다

## 어떻게 풀었나

### 추론을 완전히 로컬로

두 모델을 **Ollama에서 실행**합니다.

| 모델 | 역할 |
|---|---|
| Qwen2.5 | 자연어 목표를 실행 계획으로 분해 |
| LLaVA | 화면을 보고 어떤 요소를 조작할지 판단 |

**클라우드 모델 API 호출은 0건입니다.** 고객 화면과 작업 문맥이 외부로 나가지 않습니다.

### 픽셀과 DOM을 결합 — Set-of-Mark

DOM만으로도, 스크린샷만으로도 부족했습니다. 둘을 합쳤습니다.

1. 클릭 가능한 DOM 요소를 추출하고
2. 스크린샷 위 해당 위치에 **번호를 붙여** 렌더링하고
3. 모델에게 "몇 번을 클릭할지" 묻습니다

모델은 전체 화면의 좌표를 추측하지 않고 **제한된 후보 중 하나를 고릅니다.** 선택지를 좁히는 것이 정확도를 올리는 가장 확실한 방법이었습니다.

### 실패를 다음 실행의 자산으로

한 번에 성공하지 못할 것을 전제로 4단계 폴백을 만들었습니다.

```
1. 학습된 셀렉터    ← 과거에 성공한 것
2. Vision (LLaVA)
3. 텍스트 매칭
4. 좌표 클릭
```

그리고 성공한 좌표에서 **CSS 셀렉터를 역추적**해 SQLite에 신뢰도와 함께 기록합니다. 같은 사이트를 다시 방문하면 1번 경로가 먼저 시도되고, 실행할수록 빨라집니다.

## 적용 사례

계측 검증에 확장 적용했습니다. 실제 커머스 사이트의 사용자 플로우를 자율 탐색하며 `dataLayer` 이벤트를 수집하는 용도였습니다.

- 대상: 국내 주얼리 브랜드, 글로벌 F&B 프랜차이즈의 모바일 웹
- 내부 실행 기준 **33개 이벤트 중 80.5% 자동 검증 커버리지**

이 확장이 [GA4 Event Validator](../ga4-validator/)로 이어집니다.

## 이 프로젝트에서 배운 것

**제약이 설계를 만듭니다.** "외부 API를 쓸 수 없다"는 제약이 없었다면 상용 멀티모달 API를 붙이고 끝냈을 겁니다. 제약 때문에 Set-of-Mark와 폴백 체인을 고민했고, 결과적으로 더 나은 구조가 나왔습니다.

**모델에게 열린 질문을 던지지 않습니다.** "어디를 클릭해야 하나"는 좌표 공간 전체가 답이지만, "1번부터 12번 중 어느 것인가"는 선택지가 12개입니다. 같은 모델도 후자에서 훨씬 잘합니다.

**프로토타입이라고 명시합니다.** 실제 운영 시스템이 아니라 로컬 멀티모달 에이전트의 가능성을 확인한 실험입니다. 커버리지 80.5%는 내부 실행 기준이며 프로덕션 SLA가 아닙니다.
