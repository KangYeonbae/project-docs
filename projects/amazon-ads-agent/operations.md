## 가장 오래 붙잡은 문제 — LLM 환각

숫자와 용어의 조작이 이 시스템의 주된 실패 모드였습니다.

**규모.** 검증·교정 전용 코드 1,524줄. v3 전체 7,444줄의 **20%가 생성이 아니라 생성물 검증**에 쓰입니다. 처음부터 이 비율을 예상한 건 아니고, 실패를 하나씩 막다 보니 이렇게 됐습니다.

### 실제 장애 — 존재하는 성과를 "없음"으로 서술한 경우

**증상**
Cross-sell 섹션에서 direct conversion이 실제로 존재하는데 "직접 매출 없음"으로 서술됐습니다. 실제 데이터와 **정반대의 문장**이 리포트에 들어갔고, 운영 중 P0로 분류해 처리했습니다.

숫자를 틀린 게 아니라 존재하는 것을 없다고 서술한 경우였습니다. 금액 대조만으로는 걸리지 않는 유형입니다.

**대응**
`fact_guard`에 `_DIRECT_ABSENCE_CLAIM_RE` 정규식을 추가해, 같은 유형의 서술을 **생성 단계에서 차단**했습니다.

프롬프트를 고쳐서 "없다고 쓰지 마라"고 지시하는 방법도 있었지만 택하지 않았습니다. 프롬프트는 확률적으로 지켜지고, 정규식은 결정론적으로 지켜집니다. 외부로 나가는 문서에서는 후자가 필요했습니다.

### 남은 것

`report_qa_agent`의 금칙어 규칙에는 `source_type`, `served_search_term`, `Drill-Down`, `Top of Search`, 구매 여정, 후광 효과 등 수십 개가 쌓여 있습니다.

**한 번에 설계한 규칙이 아니라 반복 실패가 남긴 화석입니다.** 각 항목은 실제로 한 번씩 문제가 됐던 표현이고, 목록을 보면 이 시스템이 어디서 넘어졌는지가 그대로 보입니다.

## 수집 계층 — 변경 중인 외부 API 위에서의 안정화

**맥락.** 구축 시점의 Amazon 리포트 API는 개편이 진행 중이었습니다. 콘솔 화면과 응답 스펙이 함께 바뀌었고 참고할 선례가 없었습니다. 문서가 실제 동작과 맞지 않는 구간이 있었고, 그래서 **실패 유형을 하나씩 관측해 분류하는 방식**으로 대응했습니다.

| 실패 유형 | 건수 |
|---|---|
| SP-API Unauthorized (토큰 만료) | 최다 |
| catalog 200 응답 에러 | 143건 |
| Inventory 리포트 FATAL | 73건 |
| Sales 3일 초과 타임아웃 · 404 | 59건 |
| Brand Analytics FATAL | 26건 |

`200 응답 에러`는 HTTP 상태는 성공인데 본문이 에러인 경우입니다. 상태 코드만 보는 재시도 로직으로는 잡히지 않아 별도로 분류했습니다.

**결과.** 실패 유형별로 재시도 정책을 나눈 결과, 구축 기간 누적 **21,607건 중 676건을 재시도로 회수**했습니다. 남은 영구 실패 373건은 대부분 API 스펙을 역설계하던 PoC 구간에 몰려 있습니다.

## 협업 — 요구를 수용 기준으로 번역하기

리포트를 실제로 쓰는 사람은 마케터였습니다. 요구는 "리포트를 자동으로 만들어 달라"였지만, 대상마다 리포트 형식과 판단 기준이 달라 **그대로는 자동화할 대상이 정의되지 않았습니다.**

| 요구 | 설계로 옮긴 것 |
|---|---|
| 리포트 형식이 제각각이라 비교가 되지 않는다 | 기존 리포트를 직접 수집·분석해 공통 항목을 추려 **표준 리포트 생성 기준을 정립**했습니다. 자동화 이전에 문서 규격을 먼저 합의했습니다. |
| AI가 전략까지 제안해 주면 좋겠다 | 재고·시즌성·프로모션은 데이터에 없어 모델이 추정하면 틀립니다. **AI는 현상 정리까지, 전략 판단은 마케터**가 맡는 것으로 역할 경계를 합의했습니다. |
| 서술이 실제 데이터와 반대로 나온 건이 있다 | 재발 방지를 프롬프트가 아니라 **결정론적 규칙**으로 잡겠다고 정하고, `fact_guard`에 해당 서술 패턴을 차단하는 검사를 추가했습니다. |

### 사람이 개입할 지점을 남겨 두었습니다

완전 자동화 대신, AI가 만든 문장의 **근거가 되는 표와 원본 수치를 리포트에 함께 실었습니다.**

마케터가 결론을 검토할 수 있어야 자동화를 신뢰하고 계속 쓴다고 판단했습니다. 검토할 수 없는 자동화는 한 번 틀리는 순간 전부 버려집니다.
