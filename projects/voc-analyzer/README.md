## 어떤 문제였나

상담 데이터는 쌓이는데, 그걸 쓸 수 있는 형태로 만드는 일은 전부 사람 손이었습니다.

1. 상담 내역을 열어 읽고
2. 무슨 문의였는지 분류하고
3. 핵심을 요약해 정리하고
4. 리포트 문서로 옮긴다

**이 반복 작업이 응대 품질을 개선하는 일보다 더 많은 시간을 차지했습니다.** 정작 중요한 건 "어떤 문의가 늘고 있는가"를 파악해 대응하는 것인데, 거기까지 갈 시간이 남지 않았습니다.

## 어떻게 풀었나

### LLM과 규칙을 나눠 맡겼습니다

- **요약** — LLM이 담당합니다. 문맥을 읽고 핵심을 뽑는 일입니다
- **운영 분류** — 규칙으로 보강합니다. 조직에서 이미 쓰는 고정된 분류 체계가 있고, 모델이 매번 새로 판단하면 결과가 흔들립니다

같은 상담이 어제는 "배송 문의", 오늘은 "물류 관련"으로 분류되면 통계를 낼 수 없습니다. 고정된 분류는 고정된 규칙이 처리하는 편이 맞았습니다.

### 현업 도구에 맞춰 배포했습니다

이게 이 프로젝트에서 가장 중요한 판단이었습니다.

새 웹 서비스를 만들어 배포하면 계정 발급, 접근 권한, 사내 보안 검토가 따라옵니다. 도구 하나 쓰자고 넘어야 할 문턱이 많고, 그 문턱에서 대부분 멈춥니다.

**Streamlit GUI를 PyInstaller로 데스크톱 앱으로 패키징**했습니다. 비개발자가 파일을 실행하면 바로 씁니다. 서버도, 계정도, 배포 절차도 필요 없습니다.

### 결과는 이미 쓰는 곳으로

분석 결과를 새로운 대시보드에 넣지 않고 **Google Sheets 리포트**로 보냈습니다. 담당자들이 이미 스프레드시트로 일하고 있었기 때문입니다.

## 결과

**VOC/CS 반복 업무 약 40% 절감** (사내 측정 기준)

|---|---|

| 리포트 | Google Sheets 자동 반영 |

2026년 5월에 기능을 확장했습니다.

## 이 프로젝트에서 배운 것

**도입 장벽이 기능보다 중요할 때가 있습니다.** 더 좋은 웹 대시보드를 만들었어도 계정 발급 단계에서 멈췄을 겁니다. 실행 파일 하나로 만든 것이 이 도구가 실제로 쓰이게 된 이유였습니다.

**LLM에 전부 맡기지 않는 편이 결과가 일관됩니다.** 요약처럼 문맥이 필요한 일과 분류처럼 기준이 고정된 일을 나누면, 각각 잘하는 쪽에 맡길 수 있습니다.

**결과를 어디로 보낼지가 채택률을 결정합니다.** 사용자가 이미 있는 곳으로 보내면 새로 배울 것이 없습니다.

---

*40% 절감은 사내 측정 기준입니다. 클라이언트 정보와 상담 데이터는 [비공개 처리 기준](../../docs/how-to-read.md#비공개-처리-기준)에 따라 제외했습니다. 코드는 회사 자산으로 공개하지 않습니다.*
