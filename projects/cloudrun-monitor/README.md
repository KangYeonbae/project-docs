## 확인하려던 것

여러 GCP 프로젝트에 서비스를 나눠 운영하면, 상태를 확인하는 일이 번거롭습니다. 콘솔에서 프로젝트를 바꿔가며 들어가야 하고, 로그를 보려면 또 다른 화면으로 넘어갑니다.

통합 대시보드를 만들면 되는데, 여기서 **온보딩 문제**가 생깁니다.

일반적인 서드파티 관측 도구는 이렇게 시작합니다.

1. GCP에서 서비스 계정을 만든다
2. 필요한 역할을 부여한다
3. JSON 키를 다운로드한다
4. 도구에 업로드한다

**이 과정이 도입 장벽이자 보안 부담입니다.** 키 파일은 유출되면 그 자체로 인증 수단이고, 만료도 없습니다. 그리고 "이 도구에 어떤 권한을 준 건지" 시간이 지나면 아무도 기억하지 못합니다.

**사용자의 OAuth 권한만으로 이걸 대체할 수 있는가?** 이게 이 프로토타입의 질문이었습니다.

## 어떻게 만들었나

### Bring Your Own Identity

서비스 계정 키를 받지 않습니다. **사용자가 Google 로그인을 하면, 그 사용자의 권한으로 GCP API를 호출**합니다.

```
서비스 계정 방식              이 방식
────────────────            ─────────────
키 생성 → 역할 부여          Google 로그인
→ 다운로드 → 업로드          → 끝
```

| 관점 | 효과 |
|---|---|
| 온보딩 | 로그인 한 번 |
| 보안 | 장기 자격 증명을 보관하지 않음 |
| 권한 | 사용자가 이미 가진 IAM 권한을 그대로 따름 |

**권한이 자동으로 맞습니다.** 사용자가 볼 수 없는 프로젝트는 이 도구에서도 안 보입니다. 별도의 권한 동기화가 필요 없습니다.

### GCP가 진실의 원천

서비스 메타데이터를 자체 DB에 복제하지 않습니다. 필요할 때 API로 조회하고 **짧게만 캐시**합니다.

복제하면 동기화 문제가 생깁니다. 서비스가 삭제됐는데 대시보드에는 남아 있거나, 권한이 회수됐는데 여전히 보이는 상태가 됩니다.

짧은 캐시는 **권한 변경이 자연스럽게 반영된다**는 뜻이기도 합니다. IAM에서 접근을 뺐다면 다음 조회부터 안 보입니다.

### 점진적 스코프 요청

처음부터 모든 권한을 요구하지 않고, 기능을 쓸 때 해당 스코프를 요청합니다. 로그를 안 보는 사용자에게 로그 읽기 권한을 요구할 이유가 없습니다.

## 결과

| 영역 | 구현 |
|---|---|
| 인증 | Google OAuth |
| 권한 | 사용자 IAM 그대로 |
| 조회 | Cloud Run API · Cloud Logging API |
| 캐시 | 짧은 TTL |
| 화면 | 멀티 프로젝트 통합 대시보드 |

## 확인한 것과 남은 것

**확인한 것.** 사용자 OAuth만으로 관측 도구가 성립합니다. 서비스 계정 키 없이 여러 프로젝트의 Cloud Run 상태와 로그를 한 화면에서 볼 수 있습니다. 온보딩이 로그인 한 번으로 끝나는 것은 실제로 큰 차이였습니다.

**남은 것.** 이 방식은 **사용자가 접속해 있을 때만** 동작합니다. 사람이 없는 시간에 상태를 감시하고 알림을 보내는 종류의 기능은 이 구조로 만들 수 없습니다. 그건 서비스 계정이 필요한 영역입니다.

용도가 갈립니다. **탐색적 조회는 BYOI가 맞고, 상시 모니터링은 서비스 계정이 맞습니다.**

**프로토타입으로 분류한 이유.** 구조가 성립하는지 확인한 단계이며, 운영 도구로서의 요구(알림, 이력 보존, 팀 공유)는 다루지 않았습니다.
