## 어떤 문제였나

아마존에 상품을 올리려면 리스팅 이미지 여러 장과 카피가 필요합니다. 그 제작 과정이 여러 도구와 사람 사이에서 반복됐습니다.

1. 상품을 분석해 특징과 판매 포인트를 정리하고
2. 어떤 이미지를 몇 장 만들지 기획하고
3. 판매 국가에 맞게 현지화하고
4. 아마존 정책에 위배되지 않는지 검수한다

각 단계가 다른 사람, 다른 도구에서 진행되니 앞 단계의 의도가 뒤로 전달되지 않았습니다. 그리고 생성 AI를 붙이면 **이미지 9장이 서로 비슷해지는 문제**가 생겼습니다. 각각 다른 역할을 해야 하는데 같은 내용을 반복하는 겁니다.

## 어떻게 풀었나

### 이미지보다 기획서를 먼저

상품 정보를 받아 곧바로 이미지를 생성하지 않았습니다. 중간에 **구조화된 brief**를 만듭니다.

```
상품 정보 → 시각 분석 → 크리에이티브 brief → 이미지·카피 생성 → 정책 검수
                              ↑
                    사람이 검토할 수 있는 중간 산출물
```

brief에는 상품 특징, 타깃, 판매 포인트가 구조화되어 들어갑니다. 이 단계가 있으면 두 가지가 가능해집니다.

- 이미지를 만들기 전에 **방향이 맞는지 확인**할 수 있습니다
- 생성 결과가 마음에 안 들 때 **무엇이 잘못됐는지** 추적할 수 있습니다

brief 없이 바로 생성하면, 결과가 나쁠 때 프롬프트를 다시 굴리는 것 외에 할 수 있는 게 없습니다.

### 9개 결과물의 역할을 고정

각 이미지가 같은 내용을 반복하지 않도록 **슬롯별 목적을 미리 정의**했습니다.

| 슬롯 | 역할 |
|---|---|
| 썸네일 | 검색 결과에서 클릭을 만드는 첫 이미지 |
| 장점 | 핵심 판매 포인트 |
| 사용 장면 | 실제 사용 맥락 |
| ... | 각 슬롯이 서로 다른 정보를 담당 |

슬롯을 고정하니 생성 모델도 명확한 목표를 받게 됩니다. "좋은 상품 이미지를 만들어라"보다 "검색 결과에서 클릭을 유도하는 썸네일을 만들어라"가 훨씬 나은 지시입니다.

### 정책 검수를 파이프라인 안으로

아마존은 리스팅 이미지에 대한 정책이 있습니다. 만들고 나서 반려당하면 처음부터 다시 해야 합니다. **정책 검수와 이미지 품질 검사를 생성 파이프라인 안에** 넣어 자동으로 걸러냅니다.

## 결과

상품 정보 하나를 입력하면 리스팅 이미지 9장과 카피가 설계·생성되고, 정책·품질 검수까지 자동으로 진행됩니다.

| 단계 | 자동화 |
|---|---|
| 상품 분석 | 시각 분석 기반 특징 추출 |
| 기획 | 구조화된 crea­tive brief 생성 |
| 생성 | 슬롯별 이미지 9장 + 카피 |
| 현지화 | 판매 국가별 프롬프트 |
| 검수 | 정책 게이트 + 이미지 품질 QA |

## 이 프로젝트에서 배운 것

**생성형 파이프라인에는 사람이 읽을 수 있는 중간 산출물이 필요합니다.** 입력에서 최종 결과까지 한 번에 가면 디버깅이 불가능합니다. brief는 품질 관리 지점이면서 동시에 추적 지점이었습니다.

**"좋은 것을 만들어라"는 지시가 가장 나쁩니다.** 슬롯별로 목적을 고정하니 결과의 다양성과 품질이 함께 올라갔습니다. 모델에게 좁은 목표를 주는 것이 [Local Browser Agent에서 선택지를 좁힌 것](../local-browser-agent/decisions.md#02-픽셀과-dom을-결합했습니다)과 같은 원리입니다.
