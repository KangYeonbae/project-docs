## 어떤 문제였나

한 앱 안에 성격이 다른 실시간 기능이 모여 있습니다.

| 기능 | 동시성 요구 |
|---|---|
| 1:1 · 그룹 채팅 | 순서 보장, 낮은 지연 |
| 스토리 | 조회 중심, 만료 있음 |
| 투표 · 반응 | 집계 정확성 |
| 카드게임 | **턴 순서와 상태 정합성** |

**게임이 특히 다릅니다.** 채팅은 메시지가 조금 늦게 도착해도 대화가 이어지지만, 게임은 누가 먼저 냈는지, 지금 누구 차례인지가 틀리면 게임 자체가 성립하지 않습니다.

여기에 모바일이라는 조건이 붙습니다. **연결은 항상 끊깁니다.** 지하철에 들어가고, 앱이 백그라운드로 가고, 네트워크가 전환됩니다.

## 어떻게 풀었나

### 게임 상태는 서버 권위

클라이언트가 결과를 결정하지 않습니다. **Cloud Functions가 최대 8명의 턴과 카드 상태를 검증**합니다.

클라이언트에 판정을 맡기면 두 가지가 깨집니다.

1. **조작 가능성** — 클라이언트 코드는 신뢰할 수 없습니다
2. **정합성** — 두 클라이언트가 동시에 다른 판단을 내리면 상태가 갈라집니다

서버가 유일한 판정자가 되면 모든 클라이언트가 같은 상태를 봅니다. 이건 [Byeoljari에서 결제 금액을 서버에서 대조한 것](../byeoljari/architecture.md#각-단계의-방어)과 같은 원칙입니다.

### 오프라인을 정상 상태로 취급

모바일에서 연결 단절은 **예외가 아니라 기본 조건**입니다. "끊기면 에러"로 다루면 사용자는 하루에도 몇 번씩 에러를 봅니다.

Firestore의 로컬 캐시를 활용해, 끊긴 상태에서도 읽기가 되고 쓰기는 큐에 쌓였다가 재연결 시 동기화되도록 설계했습니다.

다만 **게임은 예외**입니다. 서버 권위가 필요한 액션은 오프라인에서 낙관적으로 처리할 수 없습니다. 이 구분을 기능별로 나눴습니다.

### 알림 팬아웃

그룹 채팅과 반응은 한 이벤트가 여러 사용자에게 전달돼야 합니다. FCM으로 팬아웃하되, 조용해야 할 상황(본인 액션, 음소거된 방)을 서버에서 걸러 보냅니다.

## 이 프로젝트에서 배운 것

**같은 앱 안에서도 기능마다 일관성 요구가 다릅니다.** 채팅은 최종적 일관성으로 충분하고 게임은 강한 일관성이 필요합니다. 전부에 같은 수준을 적용하면 과하거나 부족해집니다.

**오프라인을 예외로 다루면 모바일 앱은 만들 수 없습니다.** 연결이 끊기는 것을 기본 상태로 놓고, 그 위에서 어떤 기능이 동작하고 어떤 기능이 대기하는지를 정하는 순서가 맞았습니다.
