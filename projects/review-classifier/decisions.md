## 01. 전통 ML을 선택했습니다

**검토했던 것**
범용 LLM API로 감성 분류를 처리하는 방식이 이미 동작하고 있었습니다. 정확도도 나쁘지 않았고, 구현할 것도 없었습니다.

**부딪힌 문제**
비용이 처리량에 비례해 늘었습니다. 월 10만 건 기준 건당 약 8원, 월 약 80만원 수준이었습니다. 여기에 매 요청마다 외부 API 왕복 지연이 붙습니다.

그리고 이 문제의 성격을 다시 봤습니다. **긍정·중립·부정의 경계가 명확한 3-class 분류**입니다. 범용 추론이 필요한 작업이 아니라 패턴 매칭에 가깝습니다.

**결정**
scikit-learn 기반 경량 모델로 교체했습니다. 비용과 응답성이 우선순위였고, 이 문제는 그 조건에 맞았습니다.

> **정리한 것** — 라벨이 명확하고 반복량이 많은 분류에서는 작은 모델이 비용·지연·배포 난이도를 동시에 줄입니다.

## 02. 도메인 다양성을 정확도보다 먼저 확보했습니다

**검토했던 것**
한 도메인의 리뷰 데이터로 먼저 학습해 정확도를 끌어올린 뒤, 나중에 도메인을 넓히는 순서를 생각했습니다.

**부딪힌 문제**
그 도메인에서는 잘 나왔습니다. 그런데 **다른 상품군에서 정확도가 40%까지 떨어졌습니다.** 3-class 분류에서 40%는 사실상 무작위입니다.

원인은 어휘 분포였습니다. 화장품 리뷰의 "발색이 좋다"와 식품 리뷰의 "맛이 좋다"는 다른 단어를 씁니다. 한 도메인의 어휘로 학습한 모델은 다른 도메인에서 판단 근거로 삼을 특징이 없습니다.

**결정**
AI-Hub의 **5개 커머스 카테고리 리뷰 10만 건**으로 학습 범위를 넓혔습니다. 단일 도메인 최고 정확도를 포기하고 여러 도메인에서 쓸 수 있는 모델을 택했습니다.

> **정리한 것** — 한 도메인에서 90%를 만드는 것보다 다섯 도메인에서 86%를 만드는 편이 실제로는 쓸모 있었습니다.

## 03. 정확도만 보지 않고 운영 비용까지 측정했습니다

**검토했던 것**
모델 평가 지표로 정확도를 보는 것이 기본입니다.

**부딪힌 문제**
정확도가 같아도 배포 특성이 다르면 운영 비용이 달라집니다. 이 프로젝트의 출발점이 애초에 비용이었으므로, 정확도만 보고 끝내면 원래 문제에 답하지 못합니다.

**결정**
세 가지를 함께 측정하고 기록했습니다.

| 지표 | 값 | 의미 |
|---|---|---|
| 정확도 | 86.0% | 고정 테스트 분할 기준 |
| 추론 시간 | 약 10ms | 외부 API 왕복 없음 |
| 모델 크기 | 1.2MB | 서버리스 콜드 스타트에 유리 |

특히 **모델 크기**는 정확도 지표에 나타나지 않지만 배포 방식을 결정합니다. 1.2MB 아티팩트는 Cloud Run이나 Lambda에서 빠르게 뜨고 자유롭게 스케일합니다. 수 GB 모델이면 워밍업이나 상시 인스턴스가 필요합니다.

> **정리한 것** — 모델의 성능은 정확도 하나로 표현되지 않습니다. 운영 환경에서의 비용과 지연도 같은 자리에 놓고 봐야 합니다.

## 평가 방법에 대한 note

작은 테스트셋은 분할할 때마다 결과가 흔들립니다. 실험을 반복하면서 **고정된 분할과 클래스별 지표**를 쓰기로 정했습니다.

- 고정 분할 — 실험 간 비교 가능성 확보
- 클래스별 지표 — 전체 정확도가 특정 클래스의 실패를 가리는 것을 방지

3-class에서 중립 클래스는 대개 가장 어렵습니다. 전체 정확도만 보면 중립을 전부 틀려도 숫자가 그럴듯하게 나올 수 있습니다.
