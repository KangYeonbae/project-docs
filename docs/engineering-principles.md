# 엔지니어링 원칙

여러 프로젝트에서 반복해서 내린 판단을 정리한 것입니다. 처음부터 원칙이 있었던 게 아니라, 같은 실수를 두 번 하고 나서 남긴 기준에 가깝습니다.

---

## 1. 정답이 있는 것은 코드가 계산하고, 서술이 필요한 것만 모델에 맡긴다

가장 많이 반복된 판단입니다.

- **Amazon Ads Reporting Agent** — 리포트 문장은 LLM이 쓰지만, 그 안의 달러 금액은 BigQuery 원본 행으로 만든 표의 값 집합에 없으면 통과하지 못합니다. 검증 계층을 전부 결정론적 Python으로 구현했습니다
- **Byeoljari** — 만세력 변환·절기 경계·행성 위치는 정답이 있는 계산입니다. FastAPI 계산 엔진이 명식을 산출하고, Gemini는 산출된 결과를 해석만 합니다
- **Bid Master** — 엑셀 파싱은 헤더행 자동 탐색 → 컬럼명 매핑 → 인덱스 판별 순으로 규칙이 먼저 시도하고, 전부 실패할 때만 LLM으로 넘어갑니다
- **Review Sentiment Classifier** — 긍정·중립·부정처럼 경계가 명확한 분류는 LLM을 부르지 않고 1.2MB 자체 모델로 처리합니다

**왜.** 모델이 추정하기 시작하면 같은 입력에 다른 결과가 나옵니다. 유료 서비스와 클라이언트 리포트에서 그건 제품 실패입니다.

## 2. 검증자를 LLM으로 두지 않는다

생성 결과를 다른 LLM이 심사하는 LLM-as-judge는 일반적인 선택지지만 쓰지 않았습니다. **검증자를 LLM으로 두면 환각을 환각이 승인합니다.** 조작된 숫자와 바뀐 고유명사를 걸러낼 근거가 없습니다.

LLM은 서사를 고르고, 숫자의 진위는 코드가 판정합니다. 역할을 섞지 않는 것이 신뢰도의 전제라고 봅니다.

→ [Amazon Ads Reporting Agent · decisions](../projects/amazon-ads-agent/decisions.md)

## 3. 재현할 수 없는 자율성은 쓰지 않는다

에이전트가 자율적으로 경로를 정하는 구조를 먼저 만들었다가 되돌린 적이 있습니다. 같은 입력이 실행마다 다른 경로를 타면 실패를 재현할 수 없고, 재현할 수 없으면 디버깅이 성립하지 않습니다.

오케스트레이션은 Python 직선 흐름으로 두고, 에이전트 프레임워크는 LLM 호출 래퍼로만 씁니다. **프레임워크 선택의 문제가 아니라 프로덕션에서 자율성을 어디까지 허용할지의 문제**였습니다.

## 4. 성공 기준을 어디에 두느냐가 아키텍처를 결정한다

Byeoljari에서 성공 기준을 '결제 완료'가 아니라 '결제한 사람이 결과를 받는 것'으로 정의했습니다. 환불은 사용자 입장에서 실패입니다. 돈은 돌아오지만 원했던 결과는 받지 못합니다.

기준을 전달에 두자 필요한 상태가 달라졌습니다. 토큰 롤백, cron 재처리, 관리자 알림이 그래서 생겼습니다.

## 5. 자동화가 불가능한 지점은 숨기지 말고 사용자 참여로 바꾼다

Bid Master에서 일부 학교는 정보가 한글 파일로 와서 자동 추출이 불가능했습니다. 완전 자동화를 고집하면 그 학교는 아예 다룰 수 없게 되고, 사용자는 수작업으로 돌아갑니다.

자동 추출을 포기하고 사용자가 한 번 체크하면 다음부터 배지로 표시되는 토글로 바꿨습니다. **한 번의 입력이 다음 사용자에게 남는 데이터 자산이 됩니다.**

같은 이유로, 파싱 결과가 불확실한 구간은 시스템이 실제로 읽은 대상(시트명 등)을 화면에 노출합니다. 완전 자동화 대신 관측 가능성으로 신뢰를 확보하는 쪽을 택했습니다.

## 6. 사람이 개입할 지점을 남긴다

AI가 만든 결론만 보여주지 않고, 그 근거가 된 표와 원본 수치를 함께 싣습니다. 검토할 수 있어야 자동화를 신뢰하고 계속 씁니다.

Amazon Ads Reporting Agent에서는 AI의 역할을 '데이터로 확인되는 현상 정리'까지로 한정하고 전략 판단은 마케터가 맡도록 클라이언트와 합의했습니다. **성급한 결론 리스크를 프롬프트가 아니라 협업 구조로 막았습니다.**

## 7. 요구는 증상으로 오고, 내 일은 그것을 수용 기준으로 번역하는 것이다

클라이언트의 요구는 대부분 "6번째로 클릭하면 데이터가 안 나옵니다" 같은 증상으로 전달됩니다. 그대로 고치면 다음 증상이 또 옵니다.

가설을 나누고(레이스 컨디션·세션 만료·요청 취소 미처리·429·전역 상태 덮어쓰기), 검증 가능한 수용 기준으로 합의합니다(예: "20회 연속 클릭에도 미재현", "빈 화면 대신 재시도·원인 메시지·자동 재요청 중 최소 하나는 동작").

→ [Bid Master · operations](../projects/bid-master/operations.md)

## 8. 남은 부채는 문서에 적는다

숨기는 것보다 이름을 붙이는 편이 강하다고 봅니다. 각 프로젝트의 `decisions.md`에 `남은 부채` 항목이 있습니다.

- Bid Master — API 전환을 마쳤는데 Dockerfile에 chromium 설치가 남아 이미지가 불필요하게 큽니다
- Byeoljari — 게스트 결제 webhook 검증에 클라이언트 의존이 남아 있고, 저장소 기준으로 cron 스케줄 정의가 없습니다

추측으로 메우지 않는 것도 같은 원칙입니다. cron이 외부 대시보드에서 돌고 있을 가능성은 확인되지 않았으므로 "저장소 기준으로는 보장이 없다"고 그대로 적었습니다.

## 9. 에러를 처리하지 말고 원인을 없앤다

1인 제품에서 외부 코드 리뷰를 받으며 정리한 기준입니다.

> try-catch를 추가하는 것이 아니라 에러가 날 수 있는 원인 자체를 해결한다.
> 문제가 생기면 어떻게 처리할지가 아니라 왜 발생했는지를 먼저 따진다.

결제 코드를 수정할 때는 한 커밋에 여러 변경을 섞지 않고 13개 커밋으로 나눠 순차 진행했습니다. 각 단계마다 검증하고 다음으로 넘어갔습니다. **결제 로직에서는 속도보다 순서를 지키는 편이 결과적으로 빨랐습니다.**

## 10. 맞는 크기의 기술을 고른다

규칙·전통 ML·LLM·Agent를 정확도와 비용에 맞춰 조합합니다. 큰 모델이 항상 답은 아닙니다.

리뷰 감성 분류는 라벨이 명확하고 반복량이 많은 문제였습니다. TF-IDF + Linear SVM으로 고정 테스트 분할 기준 정확도 86.0%, 약 10ms 추론, 1.2MB 모델을 얻었고, 이는 서버리스 환경의 콜드 스타트와 배포 비용까지 함께 줄였습니다.

**모델의 크기가 문제 해결의 크기를 결정하지 않습니다.** 먼저 문제를 좁히고, 데이터가 충분한지 확인하고, 가장 단순한 기준선부터 측정하는 편이 빠릅니다.
