# 문서를 읽는 법

이 저장소의 문서가 어떤 규칙으로 쓰였는지 밝힙니다. 읽는 사람이 어디까지 믿어도 되는지 알 수 있어야 문서가 쓸모 있다고 봤습니다.

## 문서 구성

프로젝트마다 폴더 하나를 쓰고, 안에 최대 네 개의 문서를 둡니다.

| 파일 | 내용 | 대상 |
|---|---|---|
| `README.md` | 문제·해결·결과. 기술 배경이 없어도 읽힙니다 | 누구나 |
| `architecture.md` | 시스템 구조, 데이터 흐름, 경계 | 엔지니어 |
| `decisions.md` | 검토한 대안, 실제로 부딪힌 문제, 내린 결정, 남은 부채 | 엔지니어 |
| `operations.md` | 장애 사례, 복구 설계, 요구사항을 수용 기준으로 옮긴 과정 | 엔지니어·리드 |

문서 개수는 프로젝트마다 다릅니다. **쓸 내용이 있는 문서만 만들었습니다.** 두 달 실험한 프로토타입에 운영 문서를 붙이면 그건 기록이 아니라 포장입니다.

## 숫자에 관한 규칙

문서에 나오는 수치는 다음 중 하나입니다. 출처를 함께 적습니다.

- **실측** — 운영 DB, BigQuery, 저장소를 직접 조회한 값. 조회 시점을 명시합니다
- **기록 인용** — 사내 측정 등 제3자 기록에 남은 값. 출처를 밝힙니다
- **추정** — 계산 근거를 함께 적습니다. 예: "월 10만 건 기준"

근거를 댈 수 없는 숫자는 쓰지 않았습니다. 면접에서 가장 먼저 무너지는 것이 검증 불가능한 지표라고 생각합니다.

## 비공개 처리 기준

실무 프로젝트는 회사와 클라이언트의 자산입니다. 다음 원칙으로 가렸습니다.

경계는 하나의 질문으로 잡았습니다. **이것이 내 작업의 규모인가, 제3자의 사업 정보인가.**

**제외한 것 — 제3자의 사업 정보**

- 클라이언트사·브랜드·서비스명 → `국내 이커머스 클라이언트`, `글로벌 F&B 프랜차이즈` 같은 업종 표현으로 대체
- 광고 집행액·매출·ROAS 등 클라이언트의 실적 수치
- 고객사 수, 계약 조건, 단가, 담당자 정보
- 고객 피드백 원문 인용과 그 발생 일자
- 사내 시스템명, 내부 도메인, 저장소 경로, 테이블 원본 스키마

**남긴 것 — 내가 만든 시스템의 규모와 판단**

- 시스템 아키텍처와 데이터 흐름
- 기술 스택과 선택 이유
- 적재 행 수, 처리 건수, 코드 규모, 재시도 회수율 같은 시스템 지표
- 장애의 기술적 내용과 대응 방식

예를 들어 "1억 3,500만 행을 적재했다"는 제가 만든 파이프라인의 처리 규모지만, "이 광고에 얼마를 썼다"는 클라이언트의 영업 정보입니다. 앞은 남기고 뒤는 뺐습니다.

이미 언론에 보도된 사실은 공개된 정보로 보고 링크와 함께 남겼습니다.

코드는 어느 실무 프로젝트도 공개하지 않습니다. 개인 제품과 학습기 프로젝트는 저장소 링크를 문서에 함께 두었습니다.

## 역할 표기

혼자 만든 것과 팀으로 만든 것을 구분해서 적었습니다.

- `단독 개발` — 기획부터 배포까지 전부
- `기여도 50%` 같은 표기 — 팀 프로젝트에서 제가 맡은 범위
- 팀 프로젝트는 **제가 하지 않은 부분을 제 것으로 쓰지 않았습니다**

## 문서가 다루지 않는 것

- 코드 품질 자체 — 코드를 공개하지 않으므로 판단 근거를 드릴 수 없습니다
- 성과의 사업적 해석 — 매출 기여 같은 것은 제 판단 범위 밖입니다
- 실패한 프로젝트 — 이 저장소는 완성했거나 운영 중인 것만 다룹니다. 실패 자체는 각 문서의 `decisions.md`와 `operations.md`에 남은 부채와 장애 사례로 기록했습니다
